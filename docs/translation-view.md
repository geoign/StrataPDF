# テキスト表示の見開き翻訳ビュー（仕様案）

2026-09-29 起草。未実装。末尾の「決めてほしいこと」に答えが出たら、段階 T1 から着手する。

## 何を作るか

テキスト表示は、PDF を段落単位の要素列（見出し、段落、箇条、図、表、数式、脚注）に組み直してから WebView2 に出している。
翻訳ビューは、この要素列の各行を「左に原文、右に訳文」の2列に並べたものである。
PDF のページ単位ではなく段落単位で対にするので、原文と訳文のずれは段落の中に閉じる。

段落を行として揃える（CSS グリッドの1行に原文と訳文を置く）方式を採る。
左右を独立にスクロールさせて位置を同期させる方式も考えられる。
しかし、英語の段落と日本語の段落は高さが一致しないので、同期は近似にしかならず、長い段落の途中で左右がずれていく。
行を揃える方式なら、訳文の短い側に余白ができる代わりに、同じ段落が常に同じ高さに並ぶ。

各要素の扱いは次のとおりとする。

| 要素 | 左（原文） | 右（訳文） |
|---|---|---|
| 見出し、段落、箇条、脚注 | そのまま | 翻訳する |
| 図、表 | 画像を2列にまたがって1回だけ出す | キャプションだけ翻訳して画像の下に出す |
| 表示数式 | 2列にまたがって1回だけ出す | 翻訳しない |
| 参考文献の項目 | そのまま | 翻訳しない（書誌は訳すと検索できなくなる） |
| OCR 待ちのページ画像 | そのまま | 空欄（OCR 後に翻訳する） |

段落の中の行内数式、上付き添字、リンクは、訳文でも同じ位置に残したい。
そこで、原文の装飾部分を `<m1>…</m1>` のような番号付きタグに置き換えてから送り、訳文に同じタグがすべて戻ってきたかを検査する。
戻らなかった段落はタグを外した平文で訳し直し、段落の横に印を付ける。

## 翻訳の単位と文脈の渡し方

1段落ずつ送ると、段落をまたぐ代名詞や用語の訳が揺れる。
逆に文書全体を1回で送ると、出力が長くなって途中で切れたときの損失が大きく、表示までの待ち時間も長い。

両者の間を取り、文書の原文全体を毎回の要求の先頭に置き、その後ろで「この範囲の段落を訳せ」と 30〜50 段落ずつ依頼する。
先頭部分は要求ごとに同一なのでプロンプトキャッシュが効き、2回目以降の入力は通常単価の1割程度で読まれる（Claude の場合。OpenAI と Gemini にも同種の割引がある）。
20 ページの論文なら原文は 1.5 万トークン前後なので、全体を毎回持たせても費用の増加は小さい。
300 ページの本では原文が 15 万トークンを超えるので、文脈は「その章の原文」に絞る。

出力は段落 ID と訳文の組の JSON に固定する（Claude は `output_config.format`、OpenAI 互換 API は `response_format` の JSON スキーマ）。
ID で受けるので、段落の脱落や順序の入れ替わりは受信側で検出できる。

用語の揺れを抑えるため、翻訳の前に用語抽出を1回走らせ、原語と訳語の対（用語集）を作る。
用語集は編集画面で直せるようにし、以後の全要求の先頭部分に含める。
用語集を後から直した場合は、その語を含む段落だけ訳し直す。

## 翻訳エンジン

OCR と同じく、エンジンはトレイト（仮称 `Translator`）で抽象化し、実装を足せば選べるようにする。
HTTP クライアントは OCR のモデル取得で使っている `ureq` を流用する（Rust には Anthropic の公式 SDK がないので、Claude も HTTP を直接呼ぶ）。

実装は三つで足りる見込みである。

- **OpenAI 互換エンドポイント**：OpenAI、Gemini（OpenAI 互換口）、xAI Grok、Sakana Namazu、手元の llama.cpp サーバや LM Studio を、URL とモデル名の設定だけで切り替えられる
- **Claude API**：プロンプトキャッシュの指定と JSON 出力の指定が OpenAI 互換口と異なるので、専用に書く
- **DeepL API**：LLM ではない機械翻訳。文字数課金で、XML タグを保持する指定（`tag_handling`）がある。文脈と用語集の渡し方が LLM と異なる

ローカルのモデルをアプリの中で直接動かすことはしない。
OCR で使っている ONNX Runtime でも LLM は動かせるが、7〜10B 級のモデルの生成ループを自前で持つのは割に合わない。
llama.cpp のサーバを別に起動し、OpenAI 互換口として呼ぶ。

### 費用の目安

論文1本を入力 1.5 万トークン、出力 2.5 万トークン、本1冊をその10倍として見積もった。
思考（推論）トークンも出力として課金されるので、翻訳では思考を切るか最小にする。
なお Claude Opus 5.5 は思考を切れず、努力度（effort）の既定が `medium` なので、`low` を明示する。

Claude の単価は 2026-06 時点の公式価格表による。

| モデル | 単価（入力/出力、100 万トークンあたり） | 論文1本 | 本1冊 |
|---|---|---|---|
| Claude Haiku 4.5 | $1 / $5 | 約 $0.14 | 約 $1.4 |
| Claude Sonnet 5 | $2 / $10 | 約 $0.28 | 約 $2.8 |
| Claude Opus 5.5 | $4 / $20 | 約 $0.56 | 約 $5.6 |

Opus 5.5 は新しいトークナイザで、同じ文章のトークン数が旧世代の 1〜1.35 倍になる。上の表はこれを含めていない。
Batch API を使うと単価は半額になるが、結果が返るまで最大 24 時間かかるので、読みながら使う翻訳ビューには向かない。
本1冊を事前に訳しておく用途なら使える。

他社の単価は、下調べ（2026-09-29 の Web 調査）で得た値である。モデル名を含めて公式ページで確かめていないので、採用前に請求画面で確認する。

ただし、いずれも一世代前のモデルであり、現行世代どうしを英日で比べた公開結果は見つからなかった。
実際に使う論文を数本、候補のモデルで訳して読み比べるのが確実である。

### 未発表の原稿をどう扱うか

API に送った本文は、どの事業者でも学習には使わないとしているが、不正監視のために 30 日程度保持する（Anthropic、OpenAI、xAI）。
保持をゼロにする契約は法人向けで、個人の API 利用では選べない。
Gemini の無料枠と、Sakana Translate の Web 版は、入力を製品改善に使いうるので、原稿の送り先から外す。

そこで、送信の前に確認ダイアログを出し、「この文書は常にローカルで訳す」を文書ごとに記憶できるようにする。
ROADMAP の API 経由 OCR に書いた方針（送信前の確認を必須とする）と揃える。

## 表示と操作

テキスト表示のツールバーに「翻訳」の切替を置き、押すと2列表示に変わる。
訳文は届いた順に右列へ埋まる。
翻訳は、いま画面に出ている段落から始め、前後へ広げる。先頭から順に訳すと、論文の後半を読んでいる人は最後まで待つことになるからである。

段落ごとに「訳し直す」「原文と訳文をコピー」を右クリックで出す。
訳文の段落をクリックすると対応する原文の段落を強調し、原文の段落番号をクリックすると PDF 表示の該当位置に戻る（既存の段落単位の位置同期を使う）。

書き出しは、現在の Markdown/HTML 書き出しに「対訳」を足す。
HTML は2列の表、Markdown は原文段落の直後に訳文を引用ブロックで置く。

## 保存するもの

訳文は OCR 結果と同じく、文書ごとにローカルのキャッシュへ保存する（`%LOCALAPPDATA%\StrataPDF\data\translate\`）。
キーは「原文段落の本文のハッシュ、エンジン、モデル、訳先言語、用語集の版」とする。
OCR をやり直してリフローが変わっても、本文の変わらない段落は訳し直さずに済む。

API キーは設定ファイルに平文で置かず、Windows の資格情報マネージャーに保存する。

## 段階

| 段階 | 内容 |
|---|---|
| T1 | 2列表示、OpenAI 互換と Claude の2実装、段落 ID 付き JSON 出力、画面位置からの優先翻訳、キャッシュ、送信前確認 |
| T2 | 行内の装飾を保つタグ置換と検査、用語集（抽出、編集、差分の訳し直し）、対訳の書き出し |
| T3 | DeepL、ローカルサーバの起動補助（llama.cpp の場所とモデルを設定して、アプリから起動する） |
| T4 | 縦書きの原文への対応、Batch API による本1冊の事前翻訳 |

縦書きの原文（和書を英訳する場合）は T4 に回した。
縦書きの原文と横書きの訳文を行で揃えることはできないので、翻訳ビューでは原文も横書きに直して並べることになる。
この形で読めるものになるかは、試作してから判断したい。
